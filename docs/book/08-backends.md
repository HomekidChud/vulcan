# Chapter 8: Backends and FFI

In this chapter you'll learn what each of the three backends actually does with your program, how to read the generated code, and how to call C libraries with `extern "c"`. You'll also learn the exact rules for writing code that stays identical across backends.

## The three targets

```bash
vulcan run file.vulcan               # C backend (default): readable C -> clang -O3 -> native binary
vulcan run --target js file.vulcan   # JS backend: plain Node.js-compatible JavaScript
vulcan run --target py file.vulcan   # Python backend: Python 3 source
```

Each backend is a separate code generator, and all three enforce the same contract: identical program output. Here is a program that touches structs, methods, closures, and iterators, run on all three:

```vulcan
struct Item { text: string, done: bool }

impl Item {
    fn label(self) -> string {
        if self.done { return f"[x] {self.text}" }
        return f"[ ] {self.text}"
    }
}

fn main() {
    let items = [
        Item { text: "buy milk", done: false },
        Item { text: "ship app", done: true },
    ]
    for it in items {
        print(it.label())
    }
    let open = items.filter(|it| it.done == false)
    print("open items:", open.len())
    print("total:", items.len())
}
```

Output — the same on C, JS, and Python:

```
[ ] buy milk
[x] ship app
open items: 1
total: 2
```

## What each backend emits

- **C**: readable C you can audit with `vulcan emit file.vulcan`. Arrays become plain C vectors with bounds-checked access; structs become C structs; there is no runtime and no GC. The C is compiled with `clang -O3` (or gcc — set `VULCAN_CC` to choose) plus full hardening flags.
- **JS**: plain JavaScript. Arrays are JS arrays, f-strings become template literals, `defer` becomes `try/finally`, integer division truncates like C.
- **Python**: Python 3 source. Structs become classes, `impl` methods become real class methods, `defer` becomes `try/finally`.

## Reading the generated C

`vulcan emit` prints the C your program becomes — useful for auditing and for learning what the language costs:

```bash
vulcan emit file.vulcan
```

The output starts like this:

```c
// Generated by the Vulcan compiler
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdint.h>
#include <math.h>
#include <time.h>
#include <ctype.h>
```

Every builtin (`print`, array push, the framebuffer) is emitted inline into the file — no external runtime library, nothing hidden.

## FFI: calling C

`extern "c"` declares a C function; `link "name"` adds a library at link time:

```vulcan
extern "c" {
    fn sqrt(x: f64) -> f64
    fn floor(x: f64) -> f64
}

fn main() {
    print("sqrt(2) =", sqrt(2.0))
    print("floor(3.9) =", floor(3.9))
}
```

Output:

```
sqrt(2) = 1.41421
floor(3.9) = 3
```

On the C backend each `fn` becomes a real C prototype and the call links straight against libc. To reach any C library, declare its functions and add a `link` — this sketch is the whole setup for sqlite3 (it needs the library installed to link, so it won't run on a machine without it):

```vulcan
extern "c" { fn sqlite3_open(path: string) -> i64 }
link "sqlite3"
```

FFI parameters and returns are limited to `i64`, `f64`, `bool`, and `string` — the types with a stable C representation. On the JS and Python backends, `extern`-declared names resolve to the host's function tables (`Math.sqrt` etc. in JS, `math.sqrt` in Python), and `link` is ignored — so the FFI demo above runs on all three backends with the same output.

## Writing backend-portable code

Vulcan removes most portability traps for you — integer division truncates the same everywhere, `defer` always runs, struct method receivers behave identically. The rules that remain:

1. **Pass arrays in, get arrays back, reassign.** Arrays passed as function parameters are copied — `items = add_item(items, ...)` is the pattern that works everywhere.
2. **Copy-in, copy-out for big state.** The physics engine's `w = world_step(w, dt)` is the canonical example: the function takes the world, returns the new world, the caller reassigns.
3. **Struct method calls inside closures** are supported on every backend (fixed in 1.19.1 — the JS backend used to emit invalid `await` inside a non-async arrow; it now compiles the loop inline).
4. **Don't depend on float formatting beyond 6 significant digits** — `print` and f-strings show 6 significant digits on every backend, which is what makes `1.0 / 3.0` print `0.333333` everywhere.
5. **The environment differs.** `file_write` works natively but is in-memory in the web bundle; `net_*` needs real sockets. Same API, different environment — test on the target you ship to.

`vulcan selftest` is the enforcement mechanism: it compiles and runs the compiler's whole test suite on all three backends and fails if any output differs by a single byte.
